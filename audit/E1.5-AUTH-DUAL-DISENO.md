## a. RESUMEN EJECUTIVO

**Qué se va a cambiar.** Hoy el login de la app valida email + PIN contra una lista de usuarios que vive en JSON (`calendario_data.main.usuarios` en producción). Esa validación es 100% client-side y no genera ninguna sesión contra Supabase Auth. El módulo Osiris (Bloque E2) ahora consulta tablas relacionales en el **sandbox** (`ipsjsfkmmryzoavyasrx`) que tienen **RLS activo** (Bloque E1): la política `SELECT` exige `user_osiris_permission() IN ('admin','editor','viewer')`, lo cual requiere un `auth.uid()` real. Con la anon/publishable key (sin usuario autenticado) **todas las consultas devuelven 0 filas** aunque los datos existan (392 filas migradas en Bloque D, confirmado). E1.5 agrega: tras un login email+PIN exitoso, la app dispara en **background** una autenticación real contra Supabase Auth del sandbox, obteniendo un `access_token` que el data layer de Osiris usa como `Bearer` → RLS pasa y los datos cargan.

**Por qué es necesario.** Sin sesión Supabase Auth, Osiris relacional es inusable (devuelve 0 filas). Ya verificado: `especie`, `obtentor`, `variedad`, `cliente`, `contrato_cliente`, `contrato_plantacion` → todas 0 con anon key, HTTP 200 (firma de RLS, no de tabla vacía). El fix de columnas de hoy (`nombre`/`color_hex`/`observaciones`) es correcto pero insuficiente sin sesión autenticada.

**Cómo se hace zero-downtime.** El flujo visible para el usuario (email + PIN) **no cambia**. La autenticación Supabase es un efecto lateral asíncrono que ocurre después de que el usuario ya entró. Si falla (Auth caído, usuario sin cuenta provisionada, etc.), la app sigue funcionando igual que hoy para todos los módulos JSON-based (Tareas, Finanzas, Nóminas, Allegria, Frisku); **solo Osiris relacional** quedaría sin datos hasta que la sesión exista, degradando con un mensaje claro en vez de romper. El cambio es reversible revirtiendo 2 archivos (ver sección f) y es transparente: el usuario no ve ni un campo nuevo.

**Visión a futuro.** Este patrón es el primer escalón hacia un Auth unificado. **Pero** hoy la app habla con **dos proyectos Supabase distintos** (producción para `usuarios`/Finanzas/Nóminas, sandbox para Osiris). Una sesión Supabase Auth es **por proyecto**: la sesión del sandbox no autentica contra producción. Para Osiris-solo (sandbox) esto es suficiente ahora; la unificación real exige decidir qué proyecto es el "Auth de verdad" (ver decisión pendiente #6).

## b. ESTADO ACTUAL (login hoy)

### Flujo paso a paso

```
┌─ Pantalla de login (App.jsx, render ~2530) ─────────────────────┐
│  Input: email  +  input: PIN (4 dígitos, type=password)         │
└───────────────┬─────────────────────────────────────────────────┘
                │ click "Entrar" / Enter → handleLogin()  (App.jsx ~2005)
                ▼
   1. emailInput = loginEmail.trim().toLowerCase()
   2. w = WORKERS.find(email === emailInput)         ← WORKERS = lista en memoria
        └─ si no existe → "Email no reconocido" + auditLog(login_fallido)
   3. pinOk   = getPinActivo(w)  =  pinsPersonalizados[w.nombre] || w.pin   (~1987)
      pinTemp = pinsPersonalizados[w.nombre + "_temp"]
   4. ¿loginPin === pinOk?  → login normal
      ¿loginPin === pinTemp? → login con PIN temporal (fuerza cambio de PIN)
        └─ si ninguno → "PIN incorrecto" + auditLog(login_fallido)
   5. Login normal:
        setUsuarioActual(w)
        sessionStorage.setItem('mediterra_usuario', w.nombre)

        auditLog("login")
   6. (PIN temporal) → setWorkerPendiente(w) + modal "cambiar PIN" antes de entrar
                                                          (handleCambiarPin ~2061)
```

### Restauración de sesión (sin re-login)
- `sessionStorage['mediterra_usuario']` guarda el **nombre**. Al recargar (App.jsx ~1623 y ~1680), si hay nombre guardado y `usuarios` ya cargó, se hace `setUsuarioActual(worker)` sin pedir PIN otra vez. También restaura `mediterra_modulo`.
- **No hay token ni expiración.** La "sesión" es solo el nombre en sessionStorage. Vive hasta cerrar la pestaña o logout.

### Carga de permisos por módulo
- `usuario.modulos` (array, ej. `["tareas","osiris","finanzas"]`) decide qué módulos ve.
- `usuario.tab_permisos[modulo][tabId]` = `"editar"|"ver"|...` para permisos finos por tab.
- `usuario.rol` (`admin|editor|gerente_tecnico|consulta`) + `usuario.esCFO`.
- En Finanzas además: `usuario.empresas_permitidas` (array; null/vacío = todas).
- Todo esto vive en el objeto usuario, que se arma en el merge de carga (ver abajo).

## c. ESTADO PROPUESTO (login con auth dual)

```
┌─ Pantalla de login (SIN CAMBIOS visibles) ──────────────────────┐
│  Input: email  +  input: PIN                                    │
└───────────────┬─────────────────────────────────────────────────┘
                │ handleLogin()  — validación email+PIN IDÉNTICA a hoy
                ▼
   [TRANSPARENTE AL USUARIO]  setUsuarioActual(w) + sessionStorage  ← igual que hoy
                │
                │  ── al terminar el login normal, FIRE-AND-FORGET ──
                ▼
   [BACKGROUND, async, no bloquea la UI]
   ensureSupabaseSession(w)  (helper NUEVO, propuesto):
     1. ¿w.modulos incluye "osiris"? si NO → no hacer nada (no necesita sesión)
     2. Buscar credencial Supabase del usuario:
          - email = w.email
          - password = (recuperado de forma segura — VER DECISIÓN #2)
     3. POST {SANDBOX_URL}/auth/v1/token?grant_type=password
          headers: apikey: <sandbox anon>
          body: { email, password }
        → 200: { access_token, refresh_token, expires_at }
        → 400/401: usuario sin cuenta o credencial inválida (VER edge cases)
     4. Guardar token en memoria + sessionStorage (ej. 'sb_osiris_token')
     5. (opcional) refresco silencioso antes de expirar
                │
                ▼
   [DATA LAYER OSIRIS usa el token]
   osiris-data-layer.js → Authorization: Bearer <access_token>  (en vez de anon)
     → RLS evalúa user_osiris_permission() con auth.uid() real → datos cargan ✓
     → si no hay token → degradar: usar anon (0 filas) + mensaje "Conectando…" / "Sin sesión"
```

**Transparente al usuario:** la pantalla de login, el campo PIN, el flujo de entrada, la restauración de sesión. Nada nuevo en pantalla.
**Background (invisible):** el `signInWithPassword`, el guardado del token, el refresco, el cambio de header en el data layer.

### Schema sugerido — `user_supabase_credentials`
Tabla para mapear cada usuario de la app a su cuenta Supabase Auth y permitir el `signInWithPassword` en background.

```sql
CREATE TABLE public.user_supabase_credentials (
  app_user_email   TEXT PRIMARY KEY,          -- email del usuario en la app (lowercase)
  supabase_user_id UUID NOT NULL,             -- FK lógica a auth.users.id
  email            TEXT NOT NULL,             -- email usado en Supabase Auth (= app_user_email, decisión 1 de Angelo)
  password_enc     TEXT NOT NULL,             -- password ALEATORIO, almacenado cifrado (NO el PIN)
  enc_version      SMALLINT NOT NULL DEFAULT 1,-- versión del esquema de cifrado (rotación futura)
  activo           BOOLEAN NOT NULL DEFAULT TRUE,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- FK real opcional (auth.users vive en schema auth):
--   ALTER TABLE ... ADD CONSTRAINT fk_sb_user
--     FOREIGN KEY (supabase_user_id) REFERENCES auth.users(id) ON DELETE CASCADE;
-- RLS: esta tabla NO debe ser legible por anon ni por usuarios normales.
--   Idealmente solo accesible vía Edge Function con service_role (VER decisión #2).
```

**Estrategia de cifrado recomendada (sin implementar) — y su problema de fondo:**

⚠️ **Bloqueante arquitectónico:** la app es **frontend-only** (CRA + Supabase, sin backend propio). Un frontend **no puede** guardar de forma segura una llave para descifrar `password_enc`: cualquier llave embebida en el bundle JS es pública. Por lo tanto **"guardar el password cifrado y descifrarlo en el cliente" no es seguro** — equivale a guardarlo en claro.

Opciones reales (para que Angelo elija — DECISIÓN #2):
- **Opción A (recomendada): Supabase Edge Function.** Una función server-side recibe `{email, PIN}`, valida el PIN, y hace el `signInWithPassword` con el password real (que vive solo server-side, cifrado con secret de la función). Devuelve el `access_token` al cliente. El cliente nunca ve el password. Requiere desplegar 1 Edge Function (Deno) — nueva pieza de infra, pero es el único camino verdaderamente seguro para un front sin backend.
- **Opción B: password = derivado determinístico del PIN.** `password = HMAC(secret_servidor, email+PIN)`. Pero el `secret_servidor` tiene el mismo problema (no puede vivir en el front) → también requiere Edge Function. Y el PIN de 4 dígitos es débil (10⁴ espacio).
- **Opción C: aceptar el password en claro/“ofuscado” en una tabla no-anon + RLS estricta.** Más simple, peor seguridad. Solo defendible si el sandbox no tiene datos sensibles y es ambiente de transición. **No recomendada para el patrón unificado futuro.**
- **Opción D: magic link / OTP por email** en vez de password. Rompe la transparencia (el usuario tendría que revisar email) → choca con el requisito "no nota nada distinto".

> Mi recomendación honesta: **Opción A (Edge Function)**. Es la única que respeta a la vez (seguridad real) + (transparencia al usuario) + (front sin backend). Detalle en sección g, decisión #2.

## e. EDGE CASES IDENTIFICADOS

1. **Supabase Auth caído al momento del login.** `signInWithPassword` falla → `ensureSupabaseSession` captura el error, NO bloquea el login email+PIN (ya entró). Osiris muestra estado "Sin conexión, reintentando". El resto de la app intacta. Reintento con backoff.
2. **Usuario con email+PIN válido pero SIN cuenta Supabase (legacy).** El 400/401 de `/token` se trata como "no provisionado". Osiris degrada a mensaje "Tu cuenta aún no tiene acceso a Osiris relacional" (no error duro). Decisión #3 define si se auto-provisiona o queda manual.
3. **Sesión Supabase expira pero la sesión email+PIN sigue activa.** El data layer recibe 401 → intenta `refresh_token` (silencioso) → si el refresh también expiró, re-ejecuta `ensureSupabaseSession` (re-login background). El usuario no se entera. Si todo falla, degrada como caso 1.
4. **Usuario nuevo creado después del rollout.** Hoy se crean desde el Panel de Permisos (escribe en `usuarios`). Necesita un hook que, al crear el usuario, también cree su cuenta Supabase + fila en `user_supabase_credentials` + `user_permissions`. Decisión #3. Mientras no exista el hook, el usuario nuevo cae en el caso 2 (degradado, no roto).
5. **Revocar acceso (empleado se va).** Hoy: `desactivado=true` en `usuarios`. Para Supabase hay que además: borrar/deshabilitar la cuenta `auth.users` (o poner `user_permissions.permiso='none'`) y `activo=false` en credenciales. Si no se hace atómicamente, queda una ventana donde el ex-empleado aún tiene sesión válida en Osiris. Decisión #4 (revocación atómica).
6. **El password aleatorio guardado se corrompe/pierde.** `signInWithPassword` falla permanentemente para ese usuario → caso 2. Mitigación: poder re-generar password (reset admin) que actualiza `auth.users` + `password_enc`. Necesita el mismo canal server-side (Edge Function/service_role).
7. **[Descubierto] Dos proyectos Supabase distintos.** La sesión Auth es por proyecto. La sesión del **sandbox** no sirve para las tablas de **producción** (`usuarios`, Finanzas, Nóminas). Para Osiris-solo está bien. La unificación futura debe decidir el proyecto canónico de Auth (decisión #6).
8. **[Descubierto] `mailer_autoconfirm=false` en el sandbox.** Si se provisiona vía `signUp()` público, el usuario queda **no confirmado** y NO puede hacer `signInWithPassword` hasta confirmar por email. → La provisión DEBE hacerse vía **admin API con `email_confirm:true`** (service_role), no por signUp. Refuerza la necesidad de un canal server-side.
9. **[Descubierto] `user_permissions` tiene 3 fixtures sintéticos** (`11111111…`, `22222222…`, `33333333…`, modulo=osiris, admin/editor/viewer). NO corresponden a `auth.users` reales (fueron para el testing E1 con `SET ROLE`). Hay que insertar las filas reales con los UUID de las cuentas que se creen, y decidir si se borran los fixtures. Decisión #3.
10. **Restauración de sesión al recargar (sessionStorage).** Hoy restaura usuario sin PIN. El token Supabase en sessionStorage puede haber expirado → al restaurar hay que re-asegurar sesión (modificación en ~1685). Sin esto, Osiris cargaría 0 tras un refresh de página.
11. **Email case-sensitivity.** La app compara emails en lowercase. Supabase Auth normaliza emails. `Mbecerra@grupomediterra.cl` (mayúscula en la M) debe registrarse consistentemente lowercase en `auth.users` para que el match funcione.
12. **Concurrencia / múltiples pestañas.** Varias pestañas escribiendo `sb_osiris_token` en sessionStorage (que es por-pestaña). No es un problema grave (cada pestaña hace su propio login background), pero conviene documentarlo.

## f. PLAN DE ROLLBACK (< 5 min)

El diseño está pensado para que el rollback sea trivial porque **el login email+PIN nunca se toca en su validación**; solo se le agrega una llamada fire-and-forget.

### Pasos
1. **Revertir el commit de implementación** (cuando exista): `git revert <hash>` o `git checkout main -- src/App.jsx src/data/osiris-data-layer.js`.
2. Archivos a revertir (los 2 únicos con lógica): `src/App.jsx`, `src/data/osiris-data-layer.js`.
3. **Archivos NUEVOS a ignorar/eliminar:** `src/data/supabase-auth.js` (si se creó). Como no se importa desde ningún lado tras revertir App.jsx, es inerte; se puede borrar sin riesgo.
4. **Feature flag (recomendado):** envolver `ensureSupabaseSession` tras `REACT_APP_AUTH_DUAL === 'true'`. Rollback = poner la env var en `false` y redeploy (sin tocar código). Esto baja el rollback a < 1 min. **Recomendado fuertemente.**
5. **DB:** las tablas/cuentas creadas (`user_supabase_credentials`, `auth.users`, filas `user_permissions`) **no afectan** a la app legacy si el código fue revertido (nadie las consulta). No hace falta borrarlas para el rollback funcional; se limpian aparte si se desea.

### Cómo verificar que el rollback funcionó
- Login email+PIN entra normal (cualquier usuario).
- Network tab: **no** hay request a `/auth/v1/token`.
- Osiris (si `USE_RELATIONAL=true`) vuelve a su estado previo (0 filas / mensaje), sin romper la app.
- Ningún error en consola relacionado con `supabase-auth`.

## g. DECISIONES PENDIENTES DE ANGELO

> Ninguna de estas la inventé. Cada una salió de la investigación. **No implementar hasta resolverlas.**

**DECISIÓN #1 — SDK vs fetch directo.**
¿Agregar `@supabase/supabase-js` (maneja refresh, storage, etc., pero es dependencia nueva — CLAUDE.md pide no agregar deps sin avisar) o usar `fetch` directo a GoTrue REST (cero deps, más código manual)? *Recomendación: fetch directo* para mantener el bundle pequeño y consistente con el resto de la app.

**DECISIÓN #2 — Generación + almacenamiento/cifrado de passwords (LA MÁS IMPORTANTE).**
La app es frontend-only → no puede descifrar passwords de forma segura en el cliente. Opciones A/B/C/D en sección d. *Recomendación: Opción A (Supabase Edge Function server-side que intercambia email+PIN por access_token).* Esto es una pieza de infraestructura nueva y define todo lo demás. **Necesito tu sí/no a la Edge Function antes de cualquier implementación.**

**DECISIÓN #3 — Hook de provisión de usuarios nuevos.**
Al crear un usuario en el Panel de Permisos, ¿se auto-crea su cuenta Supabase (vía Edge Function/admin API con `email_confirm:true`) + `user_supabase_credentials` + `user_permissions`? ¿O provisión manual/batch inicial y luego manual? Además: ¿borramos los 3 fixtures sintéticos de `user_permissions`?

**DECISIÓN #4 — Revocación atómica.**
Al desactivar un empleado, ¿qué hace el sistema con su cuenta Supabase? Opciones: (a) `user_permissions.permiso='none'` (instantáneo en RLS, simple), (b) deshabilitar `auth.users` (corta refresh), (c) ambas. *Recomendación: (a) como mínimo (RLS lo bloquea de inmediato) + (b) en limpieza.* Definir si es parte del mismo click de "desactivar".

**DECISIÓN #5 — Alcance del rollout inicial.**
¿Provisionar solo a los ~3-5 usuarios que realmente usan Osiris (Carol, Angelo, Nicolás, +Lorena/Lucía si aplica) o a los 13? *Recomendación: solo los de Osiris primero* (menor superficie, menor riesgo). Los demás caen en el caso 2 (degradado, no roto).

**DECISIÓN #6 — Proyecto canónico de Auth (visión unificada).**
Hoy `usuarios` vive en **producción** (`bywovqayuzodbzwsriet`) y Osiris en **sandbox** (`ipsjsfkmmryzoavyasrx`). La sesión Auth es por proyecto. Para la unificación futura: ¿el Auth canónico será producción, y Osiris migra ahí? ¿O se consolidan ambos en un proyecto? Esto no bloquea E1.5 (Osiris-solo en sandbox), pero condiciona la arquitectura. Dejar definido el norte.

**DECISIÓN #7 — Feature flag.**
¿Implementar detrás de `REACT_APP_AUTH_DUAL` para rollback instantáneo? *Recomendación: sí.*
