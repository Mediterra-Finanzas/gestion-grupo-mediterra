## 1. Endpoint

```
POST  https://ipsjsfkmmryzoavyasrx.supabase.co/functions/v1/osiris-auth
Content-Type: application/json
```

La función hace **autenticación custom** (email+PIN), así que se despliega con **`verify_jwt = false`**. El cliente la llama con el `apikey` del sandbox en el header (no necesita sesión previa — justamente sirve para crearla).

## 2. Request

```jsonc
{
  "email": "ahuerta@grupomediterra.cl",   // string, requerido
  "pin":   "1234"                          // string, requerido (se compara como string trim)
}
```

## 3. Responses

### 200 OK — sesión emitida
```jsonc
{
  "access_token":  "eyJhbGciOi...",        // JWT GoTrue (Bearer para Osiris)
  "refresh_token": "v1.M2Rk...",           // para refresco silencioso
  "expires_at":    1717430400,             // epoch segundos (de la respuesta de verify)
  "expires_in":    3600,                   // segundos hasta expirar
  "token_type":    "bearer",
  "user": {
    "email":      "ahuerta@grupomediterra.cl",
    "rol_osiris": "admin"                   // de user_osiris_accounts (admin|editor|viewer)
  }
}
```

### 400 Bad Request — request malformado
```jsonc
{ "error": "bad_request", "detail": "email y pin son requeridos" }
```
Casos: body no-JSON, falta `email` o `pin`, tipos inválidos, método ≠ POST.

### 401 Unauthorized — credenciales inválidas
```jsonc
{ "error": "invalid_credentials" }
```
Casos (NO se distinguen entre sí, por seguridad — no revelar si el email existe):
- email no encontrado en `usuarios` de producción,
- PIN incorrecto (no coincide con activo ni temporal).

### 403 Forbidden — sin acceso a Osiris
```jsonc
{ "error": "account_inactive" }
```
Casos: email+PIN válidos, pero en sandbox **no existe fila** en `user_osiris_accounts` para ese email **o** existe con `activo=false`. (Es decir: el usuario es legítimo en la app pero no está habilitado para Osiris relacional.)

### 500 Internal Server Error
```jsonc
{ "error": "internal_error", "detail": "<mensaje corto, sin secretos>" }
```
Casos: fallo de red a producción, `generate_link`/`verify` devuelve error inesperado, etc. El `detail` nunca incluye keys ni el PIN.

## 4. Lógica de validación (fiel a `App.jsx`)

Orden exacto:

```
1. Método POST + JSON válido + { email, pin } presentes ........... si no → 400
2. emailNorm = email.trim().toLowerCase()
3. GET producción calendario_data.main → { usuarios, pinsPersonalizados }
   u = usuarios.find(x => x.email?.toLowerCase() === emailNorm) ..... si no → 401 invalid_credentials
4. activePin = pinsPersonalizados[u.nombre] || u.pin               (App.jsx:1987)
   tempPin    = pinsPersonalizados[u.nombre + "_temp"]             (App.jsx:2016)
   ok   = pin.trim() === activePin
   temp = tempPin && pin.trim() === tempPin
   si !(ok || temp) → 401 invalid_credentials
5. GET sandbox user_osiris_accounts?app_user_email=eq.emailNorm    [service_role]
   si 0 filas o activo=false → 403 account_inactive
6. POST sandbox /auth/v1/admin/generate_link {type:"magiclink", email:emailNorm}  [service_role]
   → hashed_token
7. POST sandbox /auth/v1/verify {type:"magiclink", token_hash:hashed_token}  [apikey: anon sandbox]
   → { access_token, refresh_token, expires_at, expires_in }
8. 200 con la sesión + user.rol_osiris (de la fila del paso 5)
```

> Verificado hoy (read-only): los 9 usuarios objetivo tienen `pin` en su fila de `usuarios`, así que el paso 4 funciona solo con datos de producción (no depende de `WORKERS_BASE` del código).

## 5. CORS

Preflight `OPTIONS` y headers en toda respuesta:

```
Access-Control-Allow-Origin:  <origen permitido>     // ver decisión #2
Access-Control-Allow-Methods: POST, OPTIONS
Access-Control-Allow-Headers: authorization, apikey, content-type
Access-Control-Max-Age:       86400
```

`OPTIONS` responde `204` sin cuerpo. El origen permitido se controla por un secret `ALLOWED_ORIGINS` (lista separada por comas: dominio Vercel de la app + `http://localhost:3000`), con match exacto; recomiendo **no** usar `*` porque la función maneja credenciales.

## 6. Secrets / env vars (lo que Angelo configura en el Dashboard)

**Importante:** Supabase **inyecta automáticamente** en toda Edge Function las vars con prefijo `SUPABASE_` del **proyecto donde se deploya** (el sandbox). Y **prohíbe** crear secrets custom con ese prefijo. Por eso:

| Var | Origen | ¿Configurar a mano? |
|---|---|---|
| `SUPABASE_URL` | auto-inyectada (= URL sandbox) | No |
| `SUPABASE_ANON_KEY` | auto-inyectada (sandbox) — para el `apikey` del paso 7 | No |
| `SUPABASE_SERVICE_ROLE_KEY` | auto-inyectada (sandbox) — para `generate_link` y leer `user_osiris_accounts` | No (ver nota) |
| `PROD_URL` | **secret custom** — URL de producción | **Sí** |
| `PROD_ANON_KEY` | **secret custom** — anon key de producción (leer `usuarios`) | **Sí** |
| `ALLOWED_ORIGINS` | **secret custom** — orígenes CORS permitidos | **Sí** |

> **Nota sobre el service key:** si la key auto-inyectada (`SUPABASE_SERVICE_ROLE_KEY`) no resultara válida para la Admin API con el formato nuevo (`sb_secret_`), el plan B es guardar la nuestra como secret custom con un nombre **sin** prefijo `SUPABASE_` (ej. `SANDBOX_SERVICE_KEY`) y usar esa. Esto se confirma en PASO 3/4. En ningún caso va hardcodeada.

Resultado: Angelo configura **3 secrets** (`PROD_URL`, `PROD_ANON_KEY`, `ALLOWED_ORIGINS`); las 3 del sandbox son automáticas.

## 7. Rate limiting — realidad honesta

No hay rate limit **por-función out-of-the-box** en Supabase Edge Functions (solo protección DDoS de plataforma). Lo que sí aplica:
- **GoTrue Auth rate limits** del proyecto cubren `generate_link`/`verify` (límite por hora). Para 9 usuarios es holgado.
- Un rate-limit custom fino (por email/IP) requeriría estado persistente (tabla en sandbox con ventana de tiempo), porque las instancias serverless son efímeras y un contador en memoria no es confiable.

**Recomendación:** PASO 2 incluye una mitigación mínima (rechazar si faltan campos, y un tope de longitud del body); el rate-limit persistente por intentos de PIN lo dejamos como mejora opcional documentada, no bloqueante. (Relacionado: endurecer PIN es SEG-001 en `DEUDA-TECNICA.md`.)

## 8. Decisiones pendientes (antes de PASO 2)

1. **PIN temporal:** ¿la función emite sesión Osiris también cuando el usuario entra con PIN **temporal** (paso 4 `temp`)? La app hoy fuerza cambio de PIN antes de dejarlo entrar. *Recomiendo:* aceptar el PIN temporal igual (mantiene transparencia; es raro y de corta vida). Alternativa: devolver 401 hasta que cambie el PIN. **Tu decisión.**
2. **CORS origins:** necesito el/los dominio(s) exactos de la app en Vercel para `ALLOWED_ORIGINS` (además de `localhost:3000`). ¿Cuál es?
3. **403 granular:** ¿dejamos `account_inactive` cubriendo "no provisionado" y "inactivo" juntos (como acá), o prefieres distinguir `not_provisioned` vs `account_inactive`? *Recomiendo* mantenerlos juntos (menos información a un atacante).
