# E1.5 — Fase 2: Diseño del flujo de autenticación (sin passwords en clear text)

**Fecha:** 2026-06-03
**Branch:** `feat/e1.5-supabase-auth-dual` — NO push, NO merge.
**Estado:** PROPUESTA. Nada ejecutado. Espera confirmación de Angelo antes de implementar.
**Disparador:** revisión de Angelo — el script de provisión guardaba la password aleatoria en `user_auth_credentials.password` como **texto plano**. Inaceptable: cualquiera con `service_role` (o un futuro leak de RLS) leería todas las passwords.

---

## 1. El problema

El diseño anterior (sección d del doc de diseño) asumía:
> background `signInWithPassword(email, password)` → la app/Edge Function necesita **conocer** la password → hay que guardarla en algún lado.

Guardar la password (aunque sea aleatoria) implica almacenarla recuperable. En un front-only no hay forma segura de cifrarla en cliente (bloqueante ya documentado), y en la tabla queda en clear text. **El error de fondo es asumir que necesitamos la password después de crear la cuenta.**

## 2. El requisito real

Lo único que Osiris necesita es: **un `access_token` (JWT) de GoTrue con el `auth.uid()` real del usuario**, para que las políticas RLS (`user_osiris_permission()`) evalúen sus permisos. No necesitamos la password — necesitamos **una sesión**. Y una sesión se puede emitir server-side sin password.

## 3. Métodos evaluados

| Método | Cómo emite la sesión | Guarda secreto en DB | Sesión GoTrue real (refresh/revocación) | Compatible con keys nuevas (`sb_*`) | Veredicto |
|---|---|---|---|---|---|
| **A. `generate_link` + `verify`** | Admin API `generate_link(magiclink)` devuelve `hashed_token`; Edge Function lo canjea en `/auth/v1/verify` → sesión. | **No** | **Sí** (access + refresh nativos) | **Sí** (solo usa service_role) | ✅ **ELEGIDO** |
| B. JWT manual firmado | Edge Function firma un JWT (`sub=auth_user_id`, `role=authenticated`) con el JWT secret del proyecto. | No (pero hay que custodiar el JWT secret) | **No** (no hay refresh ni revocación; expiry corto a mano) | **Frágil** — los proyectos con signing asimétrico (RS256/ES256) no exponen la llave privada para firmar a mano | ❌ inferior |
| C. Guardar password cifrada (Vault/pgcrypto) | Igual que el diseño viejo pero cifrando. | Sí (aunque cifrado) | Sí | Sí | ❌ innecesario: agrega secreto que no hace falta |
| D. Magic link / OTP por email al usuario | El usuario recibe correo y hace clic. | No | Sí | Sí | ❌ rompe transparencia (el usuario tendría que ir al correo) |

> Nota sobre el método A vs D: ambos usan magic link, pero en **A la Edge Function consume el token ella misma** (`generate_link` **no envía correo**, solo genera el token; el `verify` lo canjea server-side). El usuario no ve nada. En D el link se le envía al usuario. Es la misma primitiva de GoTrue usada de dos formas distintas.

## 4. Método elegido: A — `generate_link` + `verify` (server-side, en Edge Function)

### Flujo en runtime (Fase 2, cuando se implemente)

```
Cliente (app)                         Edge Function `osiris-auth` (Deno, server-side)
─────────────                         ────────────────────────────────────────────────
login email+PIN OK
   │  POST /functions/v1/osiris-auth
   │  { email, pin }                      1. Validar PIN contra PRODUCCIÓN
   ├──────────────────────────────────▶      (lee usuarios de calendario_data.main;
   │                                          PIN ya vive ahí hoy — no se duplica)
   │                                       2. ¿activo en user_osiris_accounts? si no → 403
   │                                       3. POST {SANDBOX}/auth/v1/admin/generate_link
   │                                          { type:"magiclink", email }   [service_role]
   │                                          → { hashed_token, email_otp, ... }
   │                                       4. POST {SANDBOX}/auth/v1/verify
   │                                          { type:"magiclink", token_hash: hashed_token }
   │                                          → { access_token, refresh_token, expires_at }
   │   { access_token, refresh_token }    5. Devolver SOLO la sesión al cliente
   ◀──────────────────────────────────┤      (nunca una password — no existe una recuperable)
   │
   ▼
osiris-data-layer.js → Authorization: Bearer <access_token>
   → RLS evalúa user_osiris_permission() con auth.uid() real → datos cargan ✓
   → refresh con grant_type=refresh_token cuando expira (sesión GoTrue normal)
```

### Por qué es el más limpio y seguro
- **Cero secretos nuevos en DB.** El único secreto es el `service_role`, que la Edge Function ya necesita y vive solo en sus env vars (server-side).
- **Sesión GoTrue nativa**: trae `refresh_token` real → refresco silencioso y **revocación** (`/auth/v1/logout`, o deshabilitar la cuenta) funcionan de fábrica. El método B (JWT manual) pierde esto.
- **`generate_link` NO envía correo** → no depende de SMTP ni rompe la transparencia al usuario.
- **Compatible con el formato de keys nuevo** (`sb_secret_`/`sb_publishable_`) — no requiere el JWT signing secret (que con firma asimétrica ni siquiera está disponible para firmar a mano).

### Riesgos / notas
- **Rate limits** de `generate_link` (Auth rate limits del proyecto). Para 9 usuarios con logins esporádicos es holgado; documentar y, si hiciera falta, cachear la sesión en el cliente (sessionStorage) y solo regenerar al expirar.
- **Validación cross-project del PIN**: la Edge Function lee el PIN desde **producción** (`bywovqayuzodbzwsriet`) y emite sesión en **sandbox** (`ipsjsfkmmryzoavyasrx`). Necesita ambas keys como secrets de la función. Es la misma realidad de "dos proyectos" ya documentada (edge case #7).
- **El PIN sigue en clear text en producción** (`usuarios[].pin`) — deuda pre-existente, **fuera del alcance** de este cambio. Si se quiere endurecer, es un workstream aparte.

## 5. Cambio al schema — eliminar `password` y renombrar la tabla

La tabla deja de ser "credenciales" y pasa a ser un **mapa app↔auth + flags**. Nada sensible. Por eso, además de soltar la columna `password`, se **renombra** `user_auth_credentials → user_osiris_accounts` (el nombre viejo sugiere que guarda passwords, y ya no lo hace).

```sql
-- La tabla ya fue creada con `password text NOT NULL`. Se quita la columna y se renombra:
ALTER TABLE public.user_auth_credentials DROP COLUMN password;
ALTER TABLE public.user_auth_credentials RENAME TO user_osiris_accounts;

-- Estado final de la tabla `user_osiris_accounts` (mapa, no credenciales):
--   app_user_email text PRIMARY KEY   -- email en la app (lowercase)
--   auth_user_id   uuid NOT NULL       -- id en auth.users (para user_permissions / trazabilidad)
--   email          text NOT NULL       -- = app_user_email
--   rol_osiris     text NOT NULL CHECK (rol_osiris IN ('admin','editor','viewer'))
--   activo         boolean NOT NULL DEFAULT true   -- flag de revocación rápida
--   created_at / updated_at timestamptz
-- RLS sigue habilitado sin políticas → solo service_role la ve.
```

> Ninguna columna contiene secretos: email y UUID no son sensibles; `rol_osiris` es el mismo dato que `user_permissions` (se mantiene por conveniencia/trazabilidad, pero la **fuente de verdad de permisos es `user_permissions`**, que es lo que lee RLS).

Alternativa equivalente: crearlas **passwordless**. Recomiendo la primera (mantiene una identidad password por si algún día se necesita un reset admin), pero **sin guardar la password**.

## 7. ¿Y si en el futuro SÍ hay que guardar algo sensible?

Regla, ya no opinable: **nunca clear text.** Opciones, en orden de preferencia:
1. **No guardarlo** (como acá). El mejor secreto es el que no existe.
2. **Supabase Vault** (`vault.create_secret` / `vault.decrypted_secrets`) — cifrado gestionado, la llave nunca toca la app.
3. **pgcrypto** con la llave en Vault (no hardcodeada).
4. **Hash** (no reversible) si solo se necesita comparar, no recuperar.
